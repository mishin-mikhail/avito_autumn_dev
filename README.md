# Avito: кандидатогенерация для поиска услуг (Recall@50)

Для каждого поискового запроса решение отбирает до 50 объявлений из корпуса
(189 212 объявлений, 2 452 запроса). Метрика — Recall@50.

## Результаты

| Тег | Ноутбук | Что изменилось | Валидация | LB | md5 answer.csv |
|---|---|---|---|---|---|
| — | `01_eda_baseline` (коммит 34536a3) | v1: BM25 + локация + P(микрокатегория) | 0.842 (валидация v1) | не отправлялась | f84fb8c0… |
| `v2` | `01_eda_baseline` | стратифицированная валидация, переходы локаций, расстояние, точные фильтры | 0.8786 (честная 0.8772, валидация v2) | **0.8313** | 2de61da5… |
| `v3` | `02_ranker` | трудная валидация, символьные n-граммы, поле «услуга», город в запросе, ранкер LightGBM | | | |

Валидации разных версий различаются по составу, поэтому их цифры напрямую не сравнимы.
Валидация v2 оказалась легче бенчмарка (0.877 против 0.831 на лидерборде); в v3 схема
валидации выбирается так, чтобы для модели v2 она давала результат, близкий к лидерборду.

Каждая отправка помечена git-тегом: `git checkout v2` возвращает ровно тот код, который дал ответ.
Более поздние коммиты тег не сдвигают.

## Как запустить

**Локально** (нужно ~16 ГБ RAM; при нехватке уменьшите `batch_size` в `src/config.py` — на результат не влияет)
```bash
pip install -r requirements.txt
# положить train.parquet, benchmark_queries.parquet, benchmark_items.parquet в ./data
# (или указать папку: export DATA_DIR=/path/to/data)
git checkout v3            # версия, которую нужно воспроизвести
cd notebooks && jupyter nbconvert --to notebook --execute 02_ranker.ipynb --output 02_executed.ipynb
```
Результат: `outputs/answer.csv`, отчёт и модель — в `artifacts/`. Время на CPU:
`01_eda_baseline` — ~15 минут, `02_ranker` — ~45 минут.

**Kaggle.** Подключить датасет (папка находится автоматически внутри `/kaggle/input`),
включить Internet, в первой ячейке указать `REPO_URL` / `REPO_REF`. Для приватного
репозитория — Kaggle Secret `GITHUB_TOKEN` (fine-grained токен с правом Contents: Read-only);
токен не попадает ни в вывод, ни в `.git/config`. GPU не нужен. Для отправки — запуск
через Save Version → Save & Run All. Результат: `/kaggle/working/answer.csv`.

**Smoke-тест без настоящих данных**
```bash
python tests/make_synthetic_data.py --out data_synth
cd notebooks
DATA_DIR=../data_synth jupyter nbconvert --to notebook --execute 01_eda_baseline.ipynb --output smoke01.ipynb
DATA_DIR=../data_synth SMOKE_TEST=1 jupyter nbconvert --to notebook --execute 02_ranker.ipynb --output smoke02.ipynb
```

Переменные окружения `DATA_DIR`, `WORK_DIR`, `OUTPUT_DIR` переопределяют пути. Сеть нужна
только для установки пакетов; внешних API решение не вызывает.

## Данные и признаки: что использовано и почему

Выводы EDA (полный прогон) и решения, которые из них следуют:

* **Корпус почти не пересекается с train** (9,6% объявлений). Поиск идёт по содержанию;
  популярность и «память» по `item_id` отключаются автоматически.
* **Запросы в основном новые**: текст знаком train у 37,5% запросов бенчмарка.
  Поэтому помимо статистик по запросам нужны текстовые генераторы и обобщение по леммам.
* **Локация — сильнейший сигнал** (учёт локации поднимает Recall@50 с 0,29 до 0,72),
  но не жёсткий фильтр:
  * в 17% пар локации не совпадают;
  * в 64% таких пар локация поиска — «региональный» id, которого нет у объявлений
    (17% запросов бенчмарка);
  * остальные — соседние города (медиана 16 км).

  Отсюда признаки P(локация объявления | локация поиска) и расстояние до центра
  локации поиска.
* **Фильтры** есть у 67% запросов train и 37% бенчмарка — валидация стратифицирована.
  Фильтр разбирается на пары «Вид услуги …», «Тип услуги …», и проверяется их дословное
  наличие в параметрах объявления.
* **Категория поиска** почти всегда одна (114) — различают микрокатегории, поэтому
  используется сглаженная P(микрокатегория | запрос).
* **Доставка** практически не встречается — признак удалён.

Признаки пары «запрос — объявление»:

| Группа | Признаки |
|---|---|
| Текст | BM25 по заголовку, параметрам и описанию; доля лемм запроса, найденных в заголовке/параметрах |
| Фильтры | BM25 фильтра по параметрам; доля пар фильтра, найденных дословно |
| Категория | log P(микрокатегория \| запрос) |
| Локация | совпадение локации; P и log P перехода локаций; log расстояния |
| Качество | соответствие фильтру рейтинга, рейтинг, log числа отзывов |

## Модели и алгоритмы

1. **Лемматизация** (pymorphy3), свой список стоп-слов.
2. **Генераторы кандидатов** (~800 на запрос):
   * BM25 по полям + покрытие лемм;
   * то же с приоритетом близких объявлений;
   * близкие объявления из вероятных микрокатегорий;
   * «память» train, если корпус пересекается с train.
3. **Отбор 50 (v2)** — линейная формула над признаками. Веса подбираются покоординатным
   перебором по сетке, максимизируя Recall@50 на валидации.
4. **Отбор 50 (v3)** — LightGBM (`lambdarank` или `binary`, выбирается по отложенному фолду).
   * Обучение на фолдах запросов из train; признаки каждого фолда считаются по train без его строк.
   * Негативы: трудные (по формуле v2), символьно похожие и случайные.
   * Ранняя остановка по Recall@50 на полном пуле отдельного фолда.
   * Дополнительные признаки: BM25 по полю «услуга» (параметры без адреса), совпадение
     запроса с адресом, символьное сходство, ранги кандидата в каждом списке пула, скор и
     ранг формулы v2, признаки контекста запроса (длина, «региональность», знакомость текста,
     уверенность P(микрокатегория), плотность конкурентов), свойства объявления.
   * Пул расширен списком по символьному сходству с приоритетом близких объявлений.

## Как проверялось качество

* **Псевдо-бенчмарк из train** (2 500 запросов, md5-разбиение) повторяет доли бенчмарка
  по трём осям: знакомый/новый текст × есть ли фильтр × тип локации.
  * «Новые» тексты убираются из train целиком.
  * Позитивы подмешиваются в реальный корпус бенчмарка.
  * Статистики считаются только по train-фолду.
* **Честная оценка весов**: подбор на половине запросов, замер на другой.
* **Контроль метрики**: быстрая оценка по пулу сверяется с метрикой, посчитанной
  «как на платформе» по спискам `item_id`.
* **Согласование с лидербордом (v3).** Валидация v2 дала 0.877 при 0.831 на лидерборде.
  Гипотеза: корпус бенчмарка собран вокруг его запросов, и у настоящих позитивов много
  похожих конкурентов, а у подмешанных позитивов валидации — мало.
  * В v3 сравниваются две схемы: `injected` (как в v2) и `in_corpus` — запросы train,
    чьи выбранные объявления уже лежат в корпусе бенчмарка.
  * Выбирается схема, где отправленная модель v2 ближе к своему результату на лидерборде.
  * Ноутбук также показывает «плотность конкурентов» у запросов бенчмарка и обеих валидаций.
* **Воспроизведение v2 внутри v3**: пайплайн v3 без новых кандидатов и с весами v2
  даёт побайтно тот же `answer.csv`, что был отправлен (проверка в ноутбуке).
* **«Новые» запросы** в v3 выбираются по одному на текст — как редкие уникальные тексты бенчмарка.
* **Проверка файла**: `answer.csv` проверяется валидатором — формат, повторы, лимит 50,
  принадлежность `item_id` корпусу.

## Найденные ошибки и что с ними сделано

| Ошибка | Решение |
|---|---|
| «Региональные» локации поиска: полнота пула 0,76, Recall@50 0,42 (v1) | переходы локаций и расстояние (v2) |
| Валидация v1 перекошена по фильтрам (66% против 37% в бенчмарке) | стратификация (v2) |
| Поле параметров содержит адрес («Место оказания услуг …») и шумит — вес поля отрицательный | точное сопоставление фильтров (v2); отдельные поля «услуга» и «адрес» (v3) |
| Валидация v2 легче бенчмарка на 0.046 | схема валидации, согласованная с лидербордом (v3) |
| Опечатки и оборванные слова («расрочку», «илосос», «натяжные потолки в») | символьные n-граммы: признак и генератор кандидатов (v3) |
| Перефразировки («замена гидроаккумулятора» → «ремонт скважин») | в планах: дообученные эмбеддинги |
| Город в тексте запроса («асфальтирование севастополь», «манипулятор одинцово») | признак совпадения запроса с адресом объявления (v3) |
| Линейная формула не учитывает взаимодействия признаков (вес локации должен зависеть от её типа) | ранкер LightGBM (v3) |

## Воспроизводимость

* **Сиды и потоки.** Единый сид (`CFG.seed = 42`); число потоков BLAS фиксируется до импорта numpy.
* **Порядок без случайности.**
  * Нет итераций по `set` строк; дедупликация через `dict.fromkeys` / `np.unique`.
  * Топ-K — по ключу (скор, округлённый до 1e-6, по убыванию; `item_id` по возрастанию), ничьих не бывает.
  * Разбиения — по md5, а не по встроенному `hash()`.
* **Арифметика без платформенных различий.** Скор формулы и расстояния считаются
  поэлементными IEEE-операциями, без BLAS.
* **Результат не зависит от `batch_size`** (проверено).
* **LightGBM:** `deterministic=True`, `force_row_wise=True`, фиксированные сиды и потоки,
  без бэггинга строк; символьный словарь — без `max_features` (его отбор сортирует
  нестабильно).
* **Проверено:** md5 `answer.csv` совпадает при разных `PYTHONHASHSEED` и в окружениях
  Kaggle (numpy 2.0 / pandas 2.3) и numpy 2.4 / pandas 3.0; для v3 — также при LightGBM
  4.6 и 4.7 (деревья модели идентичны).
