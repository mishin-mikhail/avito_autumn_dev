# Кандидатогенерация для поиска услуг

Для каждого из 2 452 запросов отобрать 50 объявлений из корпуса в 189 212 объявлений. Метрика: Recall@50.

**Итог: 0,8628 на лидерборде** (тег `v6`). Пул из ~1 400 кандидатов на запрос: лексический поиск, дообученный bi-encoder, локация и P(микрокатегория). Затем ранкер LightGBM выбирает из пула топ-50.

```
запрос ─┬─ BM25 по полям, символьные n-граммы ─┐
        ├─ bi-encoder (e5-base, 2 раунда)     ├─► пул ~1 400 ─► LightGBM (55 признаков) ─► топ-50
        ├─ P(микрокатегория) + близость        │
        └─ похожие запросы train (kNN)        ─┘
```

## Как получить финальный ответ

1. `pip install -r requirements.txt`
2. Данные положить в `data/` (`train.parquet`, `benchmark_queries.parquet`, `benchmark_items.parquet`), артефакт эмбеддингов в `artifacts/embeddings_v6` (см. ниже).
3. Открыть `notebooks/06_ranker_v6.ipynb` и выполнить все ячейки: ~50 мин на CPU, 16 ГБ RAM.

Результат: `outputs/answer.csv` с md5 `d1369e3e3a84bc839dd55231cf6cfac4`.

**Артефакт эмбеддингов:** дообученная модель и её вектора (~1,6 ГБ). Ссылка отправленна вместе с решением. Собрать его заново можно на GPU (~4 ч на A100 20 ГБ): `03_embeddings.ipynb` с `EMB_VERSION = "v4"`, затем с `"v6"`.

## Данные и признаки

Выводы EDA, которые определили решение:
* **Корпус почти не пересекается с train** (9,6% объявлений) → поиск по содержанию, а не по истории объявлений.
* **62% запросов бенчмарка с новыми текстами** → нужны обобщение по леммам и эмбеддинги.
* **Локация: сильнейший сигнал, но не фильтр.** В 17% пар train локации не совпадают. У 17% запросов локация поиска «региональная»: её нет ни у одного объявления → вероятность перехода между локациями и расстояние вместо совпадения.
* **Фильтры** («Вид услуги ...») есть у 37% запросов бенчмарка → разбор на пары и точное сопоставление с параметрами.

Признаки ранкера (55): BM25 по заголовку, параметрам, описанию и полю «услуга»; символьное сходство; близость эмбеддингов; P(микрокатегория) по леммам и по похожим запросам; локация (совпадение, P перехода, расстояние в радиусах локации); рейтинг; ранг кандидата в каждом списке пула; контекст запроса (длина, знакомость текста, плотность конкурентов).
Важнее всего для ранкера (доля gain в v6): ранг по формуле v2 (60%), ранг в списке по эмбеддингам с учётом локации (18%), ранг в списке по микрокатегориям похожих запросов (3%).


## Модели

* **Лемматизация:** pymorphy3.
* **Bi-encoder:** `intfloat/multilingual-e5-base`, дообучен на парах «запрос / выбранное объявление» (InfoNCE, негативы из батча и трудные негативы).
  * Раунд 1: трудные негативы из рангов 5-50 → Recall@100 0,384 → 0,391.
  * Раунд 2: из негативов исключены объявления той же микрокатегории, среди них много на самом деле подходящих → 0,420.
* **Похожие запросы:** 30 ближайших по эмбеддингам текстов train дают своё распределение микрокатегорий. Для новых текстов оно угадывает микрокатегорию эталона первой в 67% случаев против 47% у лемм.
* **Ранкер:** LightGBM, `lambdarank` и `binary`; итог: среднее мест кандидата в запросе по обоим.

## Валидация

* **Псевдо-бенчмарк из train:** 2 500 запросов в пропорциях бенчмарка: знакомый/новый текст × фильтр × тип локации. «Новые» тексты убираются из train целиком, эталоны подмешиваются в настоящий корпус бенчмарка.
* **Схема выбрана по лидерборду:** из двух вариантов берётся тот, где отправленная v2 ближе к своему результату на LB.
* **Без утечек.** Статистики каждой выборки считаются без её строк. Запросы валидации и фолдов исключены из обучения энкодера. Соседи для kNN ищутся только среди текстов статистик.
* **Ранкер** обучается на трёх фолдах запросов, ранняя остановка на четвёртом. Валидация в обучении и выборе модели не участвует.

## Найденные ошибки

* **Региональные локации:** Recall@50 0,42 в v1 → переходы локаций (v2), «ядро» и радиус локации (v5); сейчас 0,82.
* **Валидация легче бенчмарка на 0,05:** корпус бенчмарка собран вокруг его запросов → схема валидации, согласованная с LB (v3).
* **Адрес внутри параметров шумел** (вес поля отрицательный) → отдельные поля «услуга» и «адрес» (v3).
* **Опечатки и оборванные запросы** («расрочку», «натяжные потолки в») → символьные n-граммы (v3).
* **Перефразировки** («замена гидроаккумулятора» → «ремонт скважин») → bi-encoder (v4).
* **Ложные трудные негативы** («Скупка телевизоров» для запроса «скупка б/у техники») тормозили дообучение → фильтр по микрокатегории (v6).
* **Лишние кандидаты мешали ранкеру** у обычных запросов в v5 → убраны списки без вклада в полноту (v6).

## Воспроизводимость

* Единый сид. Число потоков BLAS фиксируется до импорта numpy. Разбиения по md5.
* Топ-K по ключу «округлённый скор, затем `item_id`»: ничьих нет.
* **Близость векторов** считается на целочисленно квантованных векторах. Сумма целых чисел точна при любом порядке сложения, поэтому результат одинаков на любой машине.
* **LightGBM** 4.6.0: `deterministic=True`, `force_row_wise=True`.
* md5 `answer.csv` проверен при разных `PYTHONHASHSEED`, версиях numpy и pandas и числе потоков.
* Нейросеть в ноутбуках ответа не запускается: вектора берутся из артефакта с md5 в манифесте.
